# 未実装機能の実装計画

調査日: 2026-11-22。対象は `host-suites` のマージコミット `9910197`。
目的は既存の After Effects エフェクトをホストした際の互換性を、実測に基づいて高めること。After Effects の編集機能全体の再実装は前提にしない。

## 現状と判断上の注意

- `README.md` は CB の Effect Sequence Data を未実装、Custom UI・Channel を部分実装と記載する。AEGP は 4/36 スイートを完全実装と記載するが、これはスイート単位の集計であり、実用上の互換率ではない。
- `suites/layer.rs` と `suites/comp.rs` は固定の合成単一レイヤーを公開し、`suites/keyframe.rs` はキーフレームなしとして回答する。一方、`instance/layers.rs` はレイヤーパラメーターへの画像接続を既に提供する。この二つは区別する。
- `stub` は未実装の証拠とは限らない。例えば `host/smart_render.rs` のチェックアウト処理や `host/utility.rs` の `iterate_stub` には処理がある。関数本体と SDK 契約を確認する。
- `suites/macros.rs` の `stub_log!` は成功を返すが出力を書かない。`host/utility.rs` の blend、convolve、gaussian kernel、`suites/utility.rs` の多数の呼び出し、`host/interact.rs` の音声呼び出しは優先調査対象。実際の SDK 契約と呼び出し状況は個別に確認する。
- `README.md` のバッチサンプリングの完全実装表示と `suites/sampling.rs` の非対応ログには不整合が見られる。API 単位で検証して文書を修正する。

## フェーズ 0: 実測と安全な失敗

1. 対象プラグインを代表的な種類、OS、バージョン別に選ぶ。配布・実行権限と試験環境を確認し、プラグインごとに再現入力を固定する。
2. `aexlo inspect` の JSON トレースと `docs/inspect.md` の手順を使い、ロード、パラメーター設定、プレビュー、レンダー、終了時のスイート取得・呼び出し・エラーを採取する。必要に応じて該当箇所の診断を追加する。
3. スイート・バージョン・関数ごとに「実装済み／部分実装／安全に非対応／未検証」を記録し、利用プラグイン数、失敗の深刻度、依存、試験可能性で順序を決める。静的検索と README は候補発見に使い、網羅的な実装一覧とは扱わない。
4. 出力未初期化のまま成功を返す経路を棚卸しし、SDK の契約と実機観測に基づき、出力の初期化、適切な非対応エラー、または意味のある実装を選ぶ。エラーに変更すると互換性が変化するため、個別回帰試験を付ける。ABI・呼出規約・スイートバージョン・FFI 境界も確認する。

完了条件: 対象プラグインの再現可能な失敗一覧、関数別の状態表、誤成功経路の優先順位と回帰試験を用意する。

## フェーズ 1: 画像処理とコールバック

実測で使われているものから、`blend`、`convolve`、`gaussian_kernel` をそれぞれ SDK の数式、境界処理、アルファ、矩形、ピクセル深度、エラー契約を調べて実装する。必要なカーネル表現を決め、まず正しい CPU 実装を作り、その後に性能を測る。既存の Iterate、World Transform、Fill Matte を再利用できるか検討する。

同時に、レイヤー・パラメーターのチェックアウトと Smart Render の時間、領域、解像度、チェックインの意味を、現在の実装と SDK 契約で比較する。出力の所有権とライフタイムを試験し、必要な差分だけ補う。Effect Sequence Data は要求元プラグインと SDK の対象バージョンを先に特定し、永続データの所有権・複製・破棄・スレッド境界を設計する。

完了条件: 各関数に正常系、境界、無効引数、対応深度、並行性の必要な試験があり、実プラグインの再現ケースと AE 由来の基準画像で比較できる。未対応条件は明示的に返す。

## フェーズ 2: 読み取り可能なプロジェクトモデル

実測で AEGP のレイヤー・コンポジション情報が必要なら、ホストが渡す任意の読み取り専用コンテキストを導入する。コンポジション、レイヤー、ソース、寸法、時間、名前、順序、親子関係に安定 ID を与え、ハンドルの所有者・有効期間・無効化を設計する。既存の単一レイヤーモデルはデフォルトとして維持する。

Layer、Comp、Item、PF Interface、Stream の必要な読み取りを同じデータから返し、存在しない情報は仮値と実値を区別する。`set_layer_param` の画像接続と AEGP が見るプロジェクト構造の対応関係も定義する。書き込み API はホストに反映する仕組みが整うまでは明示的に非対応とする。

完了条件: 複数レイヤーを持つテストコンテキストで、列挙・ID・参照・時間・削除後の無効ハンドルが一貫し、既存の単一レイヤー利用が回帰しない。

## フェーズ 3: 時間とキーフレーム

必要性が確認されたら、時間を有理数で表現し、コンポジション時間とレイヤー時間の変換、範囲、オフセット、伸縮を定義する。Stream の値とキーフレームを同一モデルに結び、まず読み取り、時刻照会、線形・保持補間を追加する。ベジェ補間や特殊な値型は実際の要件と AE 基準値を揃えてから拡張する。パラメーター checkout や Smart Render の指定時刻も同じ評価器を通す。

書き込み API は、変更の適用先、競合、コールバック中の再入、トランザクションと保存責任をホスト API で定めてから実装する。

完了条件: 異なる時間スケール、負の時刻、境界、補間、レイヤー時間変換、ランダムアクセス、並列レンダーを試験し、同一時刻の各 API の値が一致する。

## フェーズ 4: 必要な機能の選択的拡張

- カラー管理: ICC、作業色空間、変換方向、アルファと精度を仕様化し、既存の sRGB 固定から明示的な設定へ移行する。参照プロファイルと AE 基準画像を用意する。
- カスタム UI: embedder のイベント配送、Drawbot の描画対象、座標・入力・ウィンドウ寿命を検証する。CLI がイベントを送らないという現状と分けて扱う。
- 音声・補助チャンネル・GPU: ホストが供給可能なデータ形式、時刻、寿命とプラットフォーム差を設計し、利用される範囲を実装する。
- スクリプト、プロジェクト編集、テキスト、カメラ、キャッシュ、非同期レンダーなどは、それぞれ実際の需要と外部依存を確認して個別設計する。After Effects 全体の再現が必要かは機能ごとに判断する。

完了条件: 機能ごとに対応範囲、未対応時の挙動、OS・SDK・スイートバージョン、再現テストと制約を文書化する。

## 共通の検証と運用

既存のユニットテスト、`cargo check --workspace`、`cargo test -p aexlo --lib` に加え、`aexlo-test` の画像比較と `docs/toolkit.md` のマトリクス・分離実行を利用する。8/16/32-bit、legacy/smart、必要な CPU/GPU と Windows/macOS を実際に利用可能な環境で試す。AE から取得した正解画像は取得条件と許容誤差を記録し、aexlo 自身で生成した画像とは区別する。商用プラグインや OS 依存テストを CI で動かせない場合は、その制約と手動検証結果を残す。

各変更は小さな単位で、SDK 根拠、失敗の再現、実装、テスト、互換性への影響、README の状態更新を揃える。実際の作業量は対象プラグインと試験環境の確定後に見積もる。
